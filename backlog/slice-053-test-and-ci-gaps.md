# Close the §10.8 test and CI gaps

## Intent

**Problem statement:** §10.8 requires e2e flows for passing a gate, a
same-field conflict and read-only mode; none exists (connect, planning, CSP,
a11y only). AGENTS.md says a new screen gets an axe scan: the person panel,
new-initiative draft, search overlay, populated initiative page, capacity
grid, banners, frozen strip, Cancelled/Closed pages, the unlocked Countries
section and open menus are unscanned. There is no size test at the volume
ceiling (200 initiatives, 200 people, 25 teams, within half the smallest
quota), no check that the build output has no inline script, `eval` or
third-party origin, and CI lacks the SBOM, licence, static-analysis and
secret-scan steps. The CSP hard-codes `https://api.github.com`, so a fork on
GitHub Enterprise (brand pack `apiBaseUrl`) would have every call blocked.

**Outcome statement:** The checks §10.8 names exist and run in CI, and the CSP
follows the brand pack's API host.

## Scope

- E2E: pass a gate; same-field conflict; read-only (token refused).
- Axe scans for the unscanned screens and states above.
- Volume-ceiling test; build-output scan; tests that the token never reaches
  console or errors and that outbound requests go only to the configured host.
- `csp-meta-tag` derives `connect-src` from the brand pack's `apiBaseUrl`.
- CI: SBOM, licence check, CodeQL, secret scan, weekly scheduled security run
  (§10.8), actions pinned.

## Decided in review (pre-implementation)

- Scanners: CodeQL, gitleaks, a licence check of the production
  dependencies (allow list MIT, ISC, Apache-2.0, BSD-2/3-Clause, 0BSD,
  BlueOak-1.0.0, CC0-1.0) and a CycloneDX SBOM. Built without new
  dependencies: `license-checker` and `@cyclonedx/cyclonedx-npm` both pull in
  packages with high `npm audit` findings, so `scripts/check-licenses.mjs`
  reads the licences from `package-lock.json` and the SBOM is `npm sbom
  --sbom-format cyclonedx`.
- Size test: smallest quota assumed 10 MiB, so the budget is 5 MiB; each
  file also stays under the Contents API's 1 MB inline limit. The dataset
  is generated by a test (200 initiatives, 200 people, 25 teams) with a
  heavy but realistic initiative: 12-month costed phases, 8 allocations, 4
  cost items, 200-character checklist notes, a 500-character description,
  every gate before the last passed. Measured: about 4.3 MB. An extreme
  profile (24-month phases, 12 allocations) is 54 KB per initiative, 10.9 MB
  in all, which would not fit the budget.
- CI: the new steps are jobs in `ci.yml` (so the aggregate `ci` check gates
  them) and `ci.yml` gains a weekly `schedule` trigger. The SBOM is
  uploaded as an artifact of the `build` job.
- Build-output check is `scripts/check-build-output.mjs`, run in the
  `build` jobs of `ci.yml` and `deploy.yml`; a Vitest test fails on any
  workflow action not pinned to a commit or a workflow without top-level
  `permissions`.
- E2E read-only means "Read-only · Access denied": the fake GitHub starts
  rejecting the token after load. The same-field conflict uses a fake
  helper that bumps a file's `sha` behind the app. A run fails on any
  request outside the app and the configured API host.
- "Versions are pinned" is met by the lockfile plus `npm ci`.

## Acceptance criteria

- [ ] Given CI, then each §10.8 item above runs, and fails on a violation.
- [ ] Given `apiBaseUrl` set to another host, then the built CSP allows that
      host and not `api.github.com`.
- [ ] Given a generated max-size dataset, then it is at most half the smallest
      quota.
- [ ] Given each new axe scan, then no violations.
