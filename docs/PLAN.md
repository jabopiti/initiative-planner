# PLAN: build order for the white-label core

An ordered, incremental path from an empty repo to the full tool described
in [SPEC.md](SPEC.md), built per [DESIGN.md](DESIGN.md). Each phase should
be its own reviewable chunk of work; don't start a phase until the
previous one's "Done when" checklist is genuinely true. Phases 3 onward
can reorder relative to each other if it's more convenient, but Phases 0–2
must come first — nothing else works without them.

## Phase 0 — Repo scaffold & tooling

- `package.json`, `vite.config.js` (single-file plugin), `tsconfig.json`
  (`checkJs`, `allowJs`, `strict: false`), `eslint.config.js`.
- `index.html` shell (nav markup, empty containers), `src/main.js` with a
  trivial "Hello world" render.
- `.gitignore` (`node_modules/`, build output).

**Done when:** `npm run dev`, `npm run build` (producing one HTML file),
`npm run lint`, and `npm run typecheck` all work against the trivial shell.

## Phase 1 — Data model, engine, and brand pack (no UI)

- `src/masterData.js` (placeholder factory), `src/terms.js` (placeholder
  gate names), the `--brand`/`--brand-font` CSS tokens.
- Calendar/working-day math, labour cost, phase/grand totals, approval-
  track resolution (SPEC §5).
- `gateTerm()`-style helper (DESIGN §2).
- Unit tests for all of the above against the placeholder master data.

**Done when:** `npm test` passes for every calculation rule in SPEC §5,
with no UI and no DOM access anywhere in the tested modules.

## Phase 2 — Persistence, export, import

- `localStorage` load/save (debounced), schema-version gate.
- Export (full JSON download) and import (validation, Replace-all vs.
  Merge, diff preview, approval-collision warning) — SPEC §8, DESIGN §3.
- Lifecycle integration tests: create → estimate → pass Gate 1 → pass
  Gate 2 → close, plus reopen and duplicate.

**Done when:** `npm test` covers the full lifecycle contract (SPEC §6),
and a hand-built export/import round-trip preserves the data exactly.

## Phase 3 — Settings screen

Roles, Countries & rates, Budget bands, General, Data (export/import UI),
Danger zone — SPEC §7.6. This screen exists before Teams/Initiatives
because those screens need editable master data to be useful to build
against.

**Done when:** every master-data entity (role, country, band) can be
added, edited, deactivated/deleted through the UI, matching SPEC §7.6.

## Phase 4 — Teams screen

Team list, team detail (roster, capacity grid with cell popover,
non-initiative-work row, cost run-rate chart) — SPEC §7.2.

**Done when:** a team can be created, staffed, and its capacity grid and
run-rate chart correctly reflect allocations made in later phases (build
a temporary initiative by hand to verify, if Initiatives isn't built yet).

## Phase 5 — Initiatives registry + creation wizard

Initiatives list (search/filter/sort/actions) and the two-step wizard —
SPEC §7.3, §7.5.

**Done when:** a new initiative can be created end-to-end through the
wizard and appears correctly in the registry.

## Phase 6 — Initiative detail

Stepper, stage banner, band panel with threshold bar, phase panels
(reusing the wizard's phase-panel rendering), month-by-month table, gate
comparison, copy-table/CSV export — SPEC §7.4.

**Done when:** an initiative can be taken through Draft → Gate 1 → Gate 2
→ Closed entirely from this screen, with every SPEC §7.4 element present
and correct.

## Phase 7 — Portfolio

Band-tile summary/filter, cost-per-month chart with year navigation,
filtered initiative table — SPEC §7.1.

**Done when:** the chart and tiles agree with the numbers shown on
Teams/Initiative-detail for the same data.

## Phase 8 — Theming & polish

System/Light/Dark toggle, dark-mode token set, accessibility pass
(keyboard navigation within tables, `aria-sort`, focus management),
responsive review.

**Done when:** every screen repaints correctly in all three theme modes
with no reload, and table keyboard navigation (SPEC §7.4, AGENTS.md
invariants) works throughout.

## Phase 9 — Demo fixture & final verification

- `examples/exports/` fictional demo JSON (one initiative per stage,
  generated by driving the real engine functions, not hand-written) plus
  its README.
- Full pass: `npm test`, `npm run lint`, `npm run typecheck`, `npm run
  build`, then a manual browser walkthrough of every SPEC.md section.

**Done when:** a fresh clone can `npm install && npm run build` and the
resulting single HTML file matches SPEC.md end to end.
